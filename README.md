# Panorama Sales

Мобильное приложение-**шахматка квартир** для отдела продаж строительной
компании Panorama (Бишкек).

Рабочий инструмент отдела продаж: показывает весь фонд квартир в виде шахматки и
списка, фиксирует, кто и с каким клиентом работает по каждой квартире, ведёт
брони со сроками и уведомляет участников процесса об изменениях.

> **Ключевое ограничение (ТЗ 1.3):** приложение не хранит, не вычисляет и не
> отображает денежных значений ни в одном слое. Подбор — только по
> характеристикам: объект, блок, этаж, комнаты, площадь, вид, отделка, статус.

## Роли

- **Менеджер (продавец)** — смотрит фонд, берёт квартиры в работу, бронирует,
  ведёт своих клиентов и сделки. Видит все квартиры, но данные чужих клиентов
  ему недоступны.
- **Администратор** — управляет объектами и квартирами, создаёт учётные записи,
  подтверждает продажи, видит всю аналитику и журнал аудита.

Учётные записи создаёт администратор; вход — по номеру телефона и паролю.
Самостоятельной регистрации нет.

## Что реализовано

- **Вход** по телефону и паролю; ролевая изоляция доступа. Экрана регистрации
  нет — учётные записи создаёт администратор.
- **Дашборд** — статистика фонда по шести статусам, активные клиенты/сделки/
  брони, истекающие брони и просроченные действия. Без денежных показателей.
- **Шахматка** по каждому ЖК: этажи × позиции, шесть статусов, фильтры
  (комнаты, статус, менеджер), переключатель «Шахматка / Список».
- **Статусы квартиры** (FR-06): Свободна · В работе · Бронь · Оформление ·
  Продана · Не для продажи (штриховка). Кнопки в карточке зависят от статуса и
  роли.
- **Бронирование** с обязательными данными клиента (фамилия, имя, телефон), срок
  брони 3 дня, лимит активных броней, автоснятие по истечении.
- **Реестр** всего фонда со вкладками (Все / Свободные / Мои / Брони / Истекают /
  Оформление), поиском и изоляцией данных клиентов.
- **Клиенты и сделки** со стадиями (Показ → Переговоры → Бронь → Оформление →
  Завершена / Отказ), звонок и WhatsApp.
- **Центр уведомлений** со счётчиком непрочитанных и deep link на карточку.
- **Админ-панель**: пользователи (создание, роли, блокировка), журнал аудита,
  мастер массового создания блока (FR-03), табличный редактор квартир (FR-04).

## Что вне объёма этого репозитория

Это мобильный клиент. Backend (REST API, PostgreSQL, FCM/APNs, S3, SMS) —
отдельный сервис. Клиент полностью работает на демо-данных (`MockPanoramaRepository`).
Реальные фото и чертежи, офлайн-кэш, экспорт XLSX и генерация PDF-карточки —
следующие итерации (v1.1–v1.2 по ТЗ).

Четыре статуса:

| Цвет | Статус | Что значит |
|------|--------|------------|
| 🟢 зелёный | Свободна | можно брать в работу и продавать |
| 🟣 фиолетовый | В работе | кто-то показывает прямо сейчас (2 часа) |
| 🟠 оранжевый | Бронь | держится за клиентом (24 часа) |
| ⚪ серый | Продана | сделка закрыта |

## Экраны

- **Объекты** — список ЖК с счётчиками по статусам (свободно / в работе / бронь / продано).
- **Шахматка** — этажи × квартиры по каждому блоку. Фильтры по комнатности и
  «только свободные». Тап по квартире открывает карточку.
- **Карточка квартиры** — планировка (рисуется на canvas), характеристики, цена
  в долларах и рядом в сомах, рассрочка, история квартиры (кто и когда брал в
  работу). Отсюда же — действия со статусом.
- **Подбор** — поиск сразу по всем объектам компании: комнатность + бюджет +
  площадь. Это прямой ответ на вопрос «а есть другие?».
- **Сделки** — свои показы и брони с обратным отсчётом.
- **Клиенты** — карточка клиента с его запросом, автоподбором подходящих квартир,
  кнопками «Позвонить» / «WhatsApp» и историей показов. Клиента можно завести
  как в этом разделе, так и прямо во время показа.

### Как течёт состояние

Всё держится на Riverpod. Ключевой провайдер — `unitsProvider`
(`StreamProvider`): он слушает `repository.watchUnits()` и раздаёт живой фонд
квартир по всем экранам. Взял кто-то квартиру в работу — поток эмитит новый
срез, и шахматка, счётчики ЖК, карточка и бейдж на вкладке «Сделки»
обновляются сами. Никаких ручных `setState` между экранами.

```
repository.watchUnits()  ──►  unitsProvider (Stream)
                                   │
        ┌──────────────────┬───────┴───────┬──────────────────┐
        ▼                  ▼               ▼                  ▼
   шахматка           карточка        счётчики ЖК       бейдж «Сделки»
```

## Слой данных — самое важное для доработки

Экраны **не знают**, откуда берутся данные. Они общаются только с интерфейсом
[`PanoramaRepository`](lib/core/data/panorama_repository.dart):

```dart
abstract interface class PanoramaRepository {
  Future<List<ComplexModel>> fetchComplexes();
  Future<List<ManagerModel>>  fetchManagers();
  Future<List<ClientModel>>   fetchClients();
  Future<ClientModel>         addClient({ ... });
  Future<List<UnitModel>>     fetchUnits();
  Stream<List<UnitModel>>     watchUnits();          // живой фонд
  Future<UnitModel>           takeToWork({ ... });   // взять в работу
  Future<UnitModel>           book({ ... });         // забронировать
  Future<UnitModel>           release({ ... });      // вернуть в фонд
  void dispose();
}
```

За ним стоят две реализации, переключаются одним флагом:

| Флаг в `app_config.dart` | Реализация | Что делает |
|--------------------------|------------|------------|
| `useMockData = true` (сейчас) | `MockPanoramaRepository` | генерит демо-фонд, имитирует коллег |
| `useMockData = false` | `ApiPanoramaRepository` | ходит в REST API по `apiBaseUrl` |

**Смысл такой развязки:** когда Panorama отдаст описание своего сервиса, править
нужно будет **только** `ApiPanoramaRepository` и `app_config.dart`. Ни один
экран не поменяется.

### Переход на реальный API

1. В [`lib/core/config/app_config.dart`](lib/core/config/app_config.dart)
   поставить `useMockData = false` и указать правильный `apiBaseUrl`.
2. В [`ApiPanoramaRepository`](lib/core/data/api_panorama_repository.dart)
   сверить пути (`/units`, `/clients`, `/units/{id}/take` и т.д.) и разбор
   ответа с тем, что реально отдаёт сервер. Сейчас они — предположение.
3. Готово. Экраны трогать не нужно.

**Realtime.** Сейчас `watchUnits()` в API-версии перечитывает фонд раз в
15 секунд (простой polling). Когда у сервера появится WebSocket — заменить
опрос на подписку в одном методе, остальной код не заденет. Это принципиально
для механики «В работе»: другой менеджер должен видеть занятую квартиру почти
сразу.

## Соглашения по коду

Стиль перенесён из основного проекта команды (Govori) — держимся его:

- Константы и утилиты — `abstract final class` (`AppColors`, `AppConfig`,
  `Money`), не классы с конструктором.
- Роутинг — `AppRouter.onGenerateRoute` со **switch-выражением** по имени
  маршрута, переходы через `AppRoutes.*`.
- Riverpod-провайдеры собраны в `core/providers/`, а не разбросаны по экранам.
- Цвета только из `AppColors`, тексты только из `AppTextStyles` — хардкод
  `Color(0xFF...)` и `TextStyle(...)` в экранах не заводим.
- Комментарии объясняют **почему**, а не что. Пишем по-русски, как вся команда.

## Как работать вместе

1. Каждая задача — в своей ветке от `main`: `feature/короткое-описание`.
2. Перед пушем прогнать `flutter analyze` и `flutter test` — оба зелёные.
3. Изменения в UI не должны лезть в слой данных, и наоборот — граница проходит
   по `PanoramaRepository`.
4. Пул-реквест в `main`, посмотрели друг у друга — влили.
