# Panorama Backend (Dart / shelf)

REST API `/api/v1` поверх PostgreSQL для «Шахматки квартир». Единый источник
правды: приложение ходит сюда, а сервис — в БД. Денежных значений нет (ТЗ 1.3).

## Требования

- Dart SDK 3.5+
- PostgreSQL с накатанной схемой (см. `../db/` — `setup.ps1`)

## Запуск

```powershell
cd backend
dart pub get
dart run bin/server.dart
```

Сервер поднимется на `http://localhost:8080/api/v1`. Проверка:

```powershell
curl http://localhost:8080/api/v1/health
```

Настройки БД берутся из переменных окружения (иначе — значения для локальной
базы из `db/setup.ps1`):

| Переменная  | По умолчанию |
|-------------|--------------|
| `PGHOST`    | localhost    |
| `PGPORT`    | 5432         |
| `PGDATABASE`| panorama     |
| `PGUSER`    | panorama     |
| `PGPASSWORD`| panorama     |
| `PORT`      | 8080         |

## Изоляция компаний

В одной базе живут несколько застройщиков. У каждой прикладной строки есть
`org_id`, и сервер подставляет его в **каждый** запрос из сессии автора —
данные компаний не пересекаются ни при чтении, ни при записи.

Три рубежа защиты:

1. **Сессия.** Токен разрешается в компанию: `sessions → users → organizations`.
   Подделать компанию в запросе нельзя — клиент её вообще не передаёт.
2. **Фильтр в SQL.** Каждый SELECT/UPDATE/DELETE содержит `org_id = @org`.
   Запрос чужой квартиры по прямому id вернёт 404 или 409, а не данные.
3. **Составные внешние ключи.** `FOREIGN KEY (complex_id, org_id) REFERENCES
   complexes (id, org_id)` и такие же на блоках, квартирах, клиентах, сделках
   и бронях. Даже при ошибке в коде БД не даст привязать квартиру к чужому ЖК
   или клиента к менеджеру другой компании.

Логины и телефоны уникальны **во всей базе**, а не внутри компании: экран
входа спрашивает только логин и пароль, компания определяется по учётке.
При заведении второй компании берите логины с префиксом (`elit.admin`) или
номер телефона.

Новая компания заводится только через БД — эндпоинта для этого нет:

```powershell
psql -U panorama -h localhost -d panorama -v ON_ERROR_STOP=1 `
     -v code=elitstroy -v name='ЭлитСтрой' `
     -v admin_name='Иванов Иван' -v admin_login='elit.admin' `
     -v admin_phone='+996 555 12-34-56' `
     -f ..\db\new_org.sql
```

Скрипт создаёт компанию и её первого администратора с паролем `0000`, который
приложение потребует сменить при первом входе.

## Аутентификация и права

Все запросы, кроме `GET /health` и `POST /auth/login`, требуют заголовок:

```
Authorization: Bearer <token>
```

Как это устроено:

1. `POST /auth/login` проверяет пароль (bcrypt в БД), генерирует случайный
   токен, кладёт в `sessions.token_hash` его **SHA-256** и возвращает сам токен
   клиенту. В базе открытого токена нет — утечка дампа не даёт доступа к API.
2. Middleware `authMiddleware` (`lib/auth.dart`, подключён в `bin/server.dart`)
   на каждом запросе хеширует пришедший токен и ищет сессию с проверкой
   `revoked_at IS NULL`, `expires_at > now()`, `users.blocked = false`,
   `users.deleted_at IS NULL`. Результат — `AuthContext` (user_id, имя, роль) —
   кладётся в `request.context`.
3. Хендлеры берут личность и роль **только** из этого контекста. Поля тела
   запроса `manager_id`, `admin_id`, `user_id`, `from_id`, `seller_id` для
   авторизации не используются: их подделывает любой клиент.

Сессия отзывается при: `POST /auth/logout`, блокировке пользователя,
смене пароля (все прочие устройства), истечении `expires_at` (30 дней).

### Кто что может

| Действие | Требование |
|---|---|
| `POST /users`, `/users/{id}/block`, `/users/{id}/role` | админ |
| `POST /users/{id}/password` | свой пароль — любой; чужой — админ |
| `POST /units/{id}/sell` | админ |
| `POST /units/{id}/status`, `POST /units/{id}` | админ |
| `POST /complexes`, `POST /blocks/bulk`, `GET /audit` | админ |
| `POST /units/{id}/release|design|extend` | держатель квартиры или админ |
| `POST /units/{id}/take|book` с `client_id` | клиент должен принадлежать автору |
| `GET /clients`, `GET /deals` | менеджер видит только свои, админ — все |
| `GET /notifications`, `/read`, `/read-all` | всегда только свой ящик |
| `POST /devices` | устройство привязывается к автору запроса |

Свои учётные записи заблокировать/разжаловать нельзя — защита от блокировки
последнего администратора.

## Эндпоинты

- `POST /auth/login` — вход по логину/паролю, выдаёт токен.
- `POST /auth/logout` — отзыв текущей сессии.
- `GET /auth/me` — кто я по мнению сервера (проверка живости токена).
- `GET/POST /users`, `/users/{id}/block|role|password` — учётные записи.
- `GET/POST /complexes`, `POST /blocks/bulk` — объекты и массовое создание.
- `GET /units` — список фонда БЕЗ истории. `?since=<ISO-8601>` отдаёт только
  квартиры, изменившиеся с этого момента (метка берётся из `updated_at`
  предыдущего ответа, поэтому часы устройства не важны).
- `GET /units/{id}` — одна квартира вместе с историей.
- `POST /units/{id}` — редактирование квартиры (админ).
- `POST /units/{id}/take|book|release|design|sell|status|extend|message` — действия.
- `POST /units/{id}/extend-request` — менеджер просит админа продлить бронь.
- `GET/POST /clients`, `GET /deals`, `POST /deals/{id}/stage` — клиенты и сделки.
- `GET /notifications`, `/notifications/{id}/read`, `/read-all` — уведомления.
- `GET /audit` — журнал аудита (админ).

```powershell
powershell -ExecutionPolicy Bypass -File ..\check_all.ps1
```

Скрипт прогоняет шесть шагов: `flutter analyze`, `dart analyze`, `flutter test`,

## Тесты

Два слоя. Быстрый — без базы и без PostgreSQL, идёт за доли секунды:

```powershell
powershell -ExecutionPolicy Bypass -File backend\run_tests.ps1 -UnitOnly
```

Полный — поднимает отдельную базу `panorama_test`, накатывает схему и данные,
затем гоняет интеграционные тесты:

```powershell
powershell -ExecutionPolicy Bypass -File backend\run_tests.ps1
```

Рабочая база `panorama` не затрагивается: скрипт откажется работать, если имя
базы не заканчивается на `_test`. Пароль суперпользователя спрашивается один
раз и нужен только чтобы пересоздать тестовую базу.

Что покрыто интеграционными тестами:

| Группа | Проверяется |
|---|---|
| Аутентификация | доступ без токена, мусорный токен, неверный пароль, хранение токена только хешем, выход, блокировка рвёт сессию, пауза после 5 неудачных попыток |
| Роли | админские действия закрыты менеджеру, менеджер видит только своих клиентов, нельзя заблокировать себя и снять с себя роль |
| Изоляция компаний | фонд и сотрудники не пересекаются, чужую квартиру не изменить, чужого сотрудника не тронуть, аудит раздельный, в базе нет ссылок между компаниями |
| Работа с квартирой | мастер создаёт квартиры, срок брони берётся из запроса, продажу подтверждает только админ, чужую бронь снимает только админ, запрос на продление доходит, лимит в 5 квартир |

Тесты вызывают тот же обработчик, что и боевой сервер (`buildHandler` из
`lib/server_app.dart`), но без открытия порта — запущенному серверу разработки
они не мешают.

## Поведение, о котором стоит знать

- **Фонд** отдаётся без истории: она нужна только в карточке квартиры, а в
  списке умножала объём ответа на число событий по каждой квартире. Приложение
  опрашивает фонд раз в 15 секунд и после первого раза запрашивает только
  изменения — если ничего не поменялось, приходит пустой список.
- **Лимиты и срок брони** читаются из таблицы `settings` и у каждой компании
  свои: `work_limit` (квартир в работе), `booking_limit` (активных броней),
  `booking_days` (срок брони по умолчанию). Если строки нет, берутся значения
  из кода — 5, 5 и 3. Меняются пока напрямую в базе:

  ```sql
  UPDATE settings SET value = '8'
   WHERE key = 'work_limit'
     AND org_id = (SELECT id FROM organizations WHERE code = 'panorama');
  ```

- **Мастер массового создания** идемпотентен: приложение присылает
  `idempotency_key`, и повторная отправка (обрыв связи, второе нажатие,
  две вкладки одновременно) возвращает результат первой операции, а не создаёт
  блок заново. Ответ в этом случае содержит `"repeated": true`.
- **Срок брони** приходит с клиента в поле `days` (1–30, по умолчанию из
  настроек компании).
  Раньше он был жёстко зашит в 3 дня, из-за чего приложение показывало один
  срок, а в базу писался другой.
- **Подбор пароля**: 5 неудачных попыток по одному логину — пауза 15 минут
  (ответ 429). Счётчик в памяти процесса и сбрасывается при перезапуске.
- **Ошибки**: любое исключение в хендлере превращается в JSON с понятным
  текстом, а не в пустой 500. Ошибки PostgreSQL переводятся: нарушение
  уникальности — 409, проверки — 422, `NOT NULL` — подсказка накатить миграции.

## Обновление уже работающей базы

Проще всего одной командой — скрипт сам поймёт, чего не хватает:

```powershell
powershell -ExecutionPolicy Bypass -File ..\db\migrate.ps1
```

Он накатывает недостающие миграции по порядку, затем печатает отчёт
`verify.sql` (изоляция компаний) и сверку `drift.sql` (база против
`schema.sql`). Что делает каждая:

| Миграция | Что меняет |
|---|---|
| `001_auth_hardening` | токены переходят на SHA-256, старые сессии отзываются |
| `002_multi_tenant` | таблица `organizations` и `org_id` во всех таблицах |
| `003_drop_legacy_company` | сносит старый механизм `companies`/`company_id` |
| `004_indexes` | индексы под push и проверку истечения броней |
| `005_cover_bigint` | цвет обложки не помещался в `integer` — падало создание объекта |
| `006_units_delta` | индекс под инкрементальную выдачу фонда |
| `007_settings_per_org` | лимиты становятся настройкой компании, а не константой |

Для новой базы миграции не нужны — `db/setup.ps1` ставит всё сразу.

## Примечания

- Защита от двойного бронирования — через сверку статуса и `version` в UPDATE
  (409 при конфликте).
- Ответ `401` означает «сессия истекла или отозвана»: клиент чистит токен и
  возвращает пользователя на экран входа.
- Мобильное приложение об `org_id` ничего не знает: изоляция целиком на
  сервере, экран входа и модели клиента не изменились.
- Роли `superadmin` (доступ ко всем компаниям) нет намеренно — компании
  заводятся только через БД.
